# Xray JSON: merge add-on servers into an existing config

## Intent

With an Xray JSON subscription (Happ and similar clients), add-on servers
(for example white-list LTE servers from a provider) can only be added as
separate configs. A client then lists them as individual servers and cannot
pick the best one by ping.

The panel template already provides a config with a balancer and a
`burstObservatory` (for example "Whitelist auto"). The add-on should
put its servers *into that config*, so the client's balancer chooses the best
server by ping among the panel's servers and the add-on's.

## Goals

- A per-add-on option naming the existing Xray config to merge into, by a
  regular expression on the config's `remarks`.
- Add-on servers become extra outbounds of that config, tagged so its balancer
  and `burstObservatory` select them with no template changes.
- Render `hysteria2://` links as Xray `hysteria` outbounds (today they are
  skipped for xray-json).
- Generic: nothing about names, flags, countries or providers in code; all of
  it comes from `addons.yml`.

## Non-goals

- No balancer, routing or observatory is generated by subpage. The panel
  template stays the single source of routing logic.
- sing-box, mihomo and base64 behaviour does not change.
- No change to how add-on servers are looked up, cached or named for other
  formats.

Note: add-ons are applied one after another to the same body, so `into` is
tested against remarks that earlier add-ons may already have rewritten;
anchor only the start of the pattern.

## Anti-goals

- Duplicate outbound tags inside one config.
- Servers silently disappearing when the target config is not found.

## Approaches considered

A. **Merge into an existing config** (chosen). Subpage appends outbounds to
the matching config. Small, keeps routing in the panel, works for any
template that has a balancer.
B. Subpage builds a full config with its own balancer and routing. Rejected:
routing logic is duplicated and the template stops being the single source.
C. Keep separate configs, only add hysteria2. Rejected: no balancing by ping.

## Design

**Config.** New optional field on an add-on (key name is the builder's call,
proposed `xray.into`): a Go RE2 regular expression, unanchored and
case-sensitive like `match`. When empty, behaviour is unchanged.

**Selecting the target.** In `mergeXray`, among the panel's configs, the first
whose `remarks` matches. If none matches, fall back to today's behaviour
(separate configs) and log a warning.

**Tag prefix.** Taken from the target config: the first selector of its first
balancer (fallback: `burstObservatory.subjectSelector[0]`). New outbounds get
`<prefix>-addon-<n>` (n counts from 1, unique within the config). If the
target has neither a balancer nor an observatory selector, treat it as "not
suitable" and fall back to separate configs with a warning, because the
servers would never be selected.

**Placement.** New outbounds are inserted after the existing outbounds that
carry the prefix and before the static ones (`direct`, `block`), matching the
order the panel produces.

**Rendering.** `Proxy.Xray()` gets a tag parameter instead of the hard-coded
`"proxy"`, and learns `hysteria2`: protocol `hysteria`, same field layout as
the panel's own hysteria outbounds (address, port, auth, TLS server name,
`salamander` obfs when present). The builder should copy the exact JSON shape
from a real panel response rather than invent it.

**Naming and quota.** Outbound tags carry no quota. The quota text goes into
the target config's `remarks` using its own template `xray.remark` (default
`{remark}`, i.e. unchanged), e.g. `{remark} · {remaining} of {limit} GB`.
Placeholders are those the add-on already supports; `{remark}` is the target's
original remarks. Unlimited and unknown usage use the same `∞` and `?` rules
as today.

**Stubs.** In this mode the placeholder configs for LIMITED/EXPIRED
add-on users are not added to `outbounds`. The target config's `remarks` gets
the stub text instead of the quota (add-on's `stubs` text), so the user can
see why no extra servers appeared.

**Several add-ons.** Each add-on with `xray.into` appends to its own matching
config in order; tag numbers continue from the highest existing
`<prefix>-addon-<n>`.

**Docs.** `addons.example.yml` and the README get the new option with a
neutral example (no lentryd names or IPs). Real `addons.yml` stays untracked
and unchanged by this work.

## Constraints

- Go 1.26, existing `internal/pkg/addon` package, conventional commits,
  `go test ./...`, `go vet ./...` and golangci-lint must pass.
- The `hysteria` outbound must be accepted by clients that already accept the
  panel's own `hysteria` outbounds (Happ); it was verified only for the
  panel's outbounds so far.

## Left to the builder

- Final option name and where it lives in the YAML.
- Exact JSON of the `hysteria` outbound; test against a captured panel
  response (with secrets removed).
- Test cases: target found, target not found, no balancer in target, several
  add-ons, duplicate tags, stub status, unlimited quota, hysteria2 with and
  without salamander.
